## Staging gestionado y recuperación

Se comprobó por nombre y referencia el destino independiente **StudyHub Staging V2**. Tenía una fila de estado, ningún plan y CAS activo. Se aplicaron por SQL explícito, en una transacción, las migraciones `202610310001`, `202611010001`, `202611020001` y `202611020002`. Se desplegó únicamente `studyhub-plan` en ese destino. La función comprueba la sesión con Auth. Sin JWT devolvió 401 y con token inválido 403. Los hashes de las migraciones están registrados. Una instalación SQL directa debe reconciliarse con el inventario de migraciones antes de usar la CLI para actualizar otro entorno. [Inventario antes y después](release-cloud-inventory.json).

**41 comprobaciones cloud** con dos usuarios sintéticos y un segundo cliente del propietario. Se agregaron 300 entregables y se reconstruyó exactamente el estado desde otro cliente. Se probaron importación local con procedencia, rechazo de hash manipulado, cola desconectada v1/v2 y Storage privado. Un ensayo transaccional copió, retiró y restauró las cuatro tablas de la cuenta sintética, comparó filas en ambas direcciones y revirtió la transacción. Después se verificó el hash del original en Storage. El estado previo de staging conservó su huella y al finalizar quedaron cero usuarios de los ensayos y cero cabeceras/eventos/versiones temporales. El campo `sql` del ejecutor identifica exclusivamente la batería SQL local. El ensayo SQL gestionado figura en la última comprobación cloud. [Cloud](release-cloud.json) · [Selector en Chrome](release-file-picker.json).

**38 comprobaciones funcionales y 7 SQL en Supabase local**. Incluyeron restauración desde archivo SQL con SHA-256 y reversión de permisos sin borrar historia. Los contenedores iniciados para el ensayo se detuvieron. Hay solapamiento entre las baterías cloud y local. [Resultados locales](release-staging.json).

## Cubo LED, software y rendimiento

El escenario aislado toma de los tres documentos externos la placa de 293 mm, el montaje en seco, la electrónica, el simulador de figuras y los requisitos de Python. Las etapas, mediciones y archivos del ensayo son ficticios. La captura del tutorial fue rechazada como verificación propia. Tras verificar una pieza sintética se liberó el montaje. Al cambiar el criterio se volvió a bloquear, conservando la versión que había sido verificada. El cambio adicional sin aprobación quedó fuera. El avance permaneció **Sin calcular** al carecer de pesos. El dominio académico empezó sin evaluaciones propias. [Paquete de revisión sintético](release-browser/cubo-sintetico.zip).

El ZIP del ejemplo pasó una segunda lectura con la biblioteca ZIP de Python. Se comprobaron CRC, tamaño y SHA-256 de JSON, Markdown y original contra el manifiesto, con cero exclusiones. La batería también generó dos ZIP para recuperar seis originales de 20 MiB de una sola tarea y fecha. Cada parte identifica el conjunto, su número y las rutas de todas las partes. Se debe conservar la misma selección y revisión. Si cambia el identificador, hay que reunir un conjunto nuevo. En una selección por período se conserva la versión de entrega que corresponde a ese período. Las versiones citadas por evidencias históricas que falten se declaran en el manifiesto. La copia JSON y los originales privados son necesarios para recuperar una cuenta.

| Medición | Resultado |
|---|---|
| Preparación de selección parcial con 999 dependencias encadenadas | De 3.738 ms a 4,9 ms para recuperar las mismas 999 referencias. Se indexaron padres y dependencias en memoria. Medición puntual en Node |
| 1.000 elementos, 999 dependencias y 60 cambios | 6.169.682 bytes, 142 eventos y 101 versiones. Validar el plan tomó 1.401 ms y proyectar el árbol 30 ms |
| Proyecto ficticio de software con 1.000 módulos en Chrome | Primera apertura 428 ms, cambio al árbol 146 ms. Heap de JavaScript observado tras abrirlo 9,3 MB |
| Carga fría en ancho de 390 px | 5,11 s con 150 ms de latencia y 160.000 bytes/s de descarga simulada. Servidor local sin compresión HTTP. Mide la primera pantalla del plan, no una red celular física |
| ZIP con cinco originales de 20 MiB en Node | 104.870.425 bytes en 1,09 s. Incremento de RSS observado de unos 69 MiB. El delta no mide el pico en un móvil |

Los ensayos de capacidad no garantizan la misma latencia en otros equipos o regiones. Se mantienen los límites v2 de 8 MiB/20.000 eventos por plan, 20 MiB por original y 100 MiB de originales por parte, con el límite adicional del ZIP. Un JSON muy grande puede requerir acotar por objetivo o período. Se conserva la copia JSON completa para restauración. ## Proveedores y pendientes por gravedad

1. **Bloqueo para publicar con IA activa.** En la ronda del 29 de octubre Gemini devolvió alta demanda en la revisión. La petición de áreas devolvió un error HTTP cuyo código exacto no se conservó. Ese error no permite distinguir saturación, cuota, modelo o petición inválida. Cloudflare devolvió una salida rechazada por el validador. Faltan los datos de terminación de esa respuesta para atribuirla a truncamiento o a incumplimiento de esquema. El código conserva diagnósticos sanitizados y rechaza resultados inválidos. Cero inferencias en esta ronda. El asistente operativo puede registrar y revisar propuestas manualmente. [Cierre histórico](../StudyHub_2_Cierre_IA_Real.md) · [Errores de Gemini](https://ai.google.dev/gemini-api/docs/troubleshooting) · [JSON Mode de Cloudflare](https://developers.cloudflare.com/workers-ai/features/json-mode/) · [Modelo de Cloudflare](https://developers.cloudflare.com/workers-ai/models/gpt-oss-120b/).
2. **Condiciones de la ventana de publicación.** Obtener autorización para el destino real y completar la copia, restauración y control de clientes especificados abajo. La prueba de staging se realizó con usuarios sintéticos. No se leyó producción ni se hizo merge, push o despliegue en Netlify.
3. **Cobertura de equipos.** Móvil físico, lector de pantalla, pico de memoria en móvil y red celular real quedan pendientes. El ensayo de archivos en Chrome automatizó la selección y comprobó los bytes. No midió la ergonomía del diálogo del sistema con una persona.

Para plantear una prueba real futura, el máximo sería de tres inferencias sintéticas independientes en staging, dos con `gemini-3.8-flash` (revisión y áreas) y una con `@cf/openai/gpt-oss-120b` (revisión del mismo intento). Cuota efectiva actual **desconocida**. Confirmar acceso y al menos dos peticiones Gemini, saldo o límite gratuito efectivo de Cloudflare con margen suficiente, ausencia de excedentes facturables y aprobación nueva. Si falla el control de cuota, falta consentimiento, hay error o respuesta incierta, detener y conservar el ID. Sin reintentos automáticos. No reutilizar el ledger anterior. El éxito de esas tres inferencias tampoco acreditaría por sí solo un asistente conversacional real de planificación.

## Publicar y poder volver atrás

1. Fijar commit y ventana autorizados. Inventariar dispositivos, pestañas antiguas y colas pendientes. Guardar borradores, parar las sesiones activas, exportar cada estado y reconciliar divergencias. Una cola inaccesible bloquea la apertura de escrituras.
2. Respaldar y cifrar base, esquema, RLS, funciones, permisos, configuración Auth y bytes de Storage. Incluir por separado `studyhub_states`, `studyhub_plan_heads`, `studyhub_plan_events`, `studyhub_plan_versions`, identificadores de objetos, propietario, revisiones y SHA-256. Restaurar en destino aislado. Comparar recuentos, historias hidratadas, hashes y denegación cruzada.
3. Aplicar únicamente migraciones faltantes en orden tras comparar el catálogo efectivo y sus hashes. Desplegar el handler real del plan con validación Auth y comprobar rechazo de token ausente/falso. Con las escrituras cerradas, instalar CAS, actualizar el cliente RPC e instalar las guardas. Conservar el permiso de escritura del plan únicamente para el handler. IA deshabilitada también en el servidor, sin credenciales de proveedores habilitadas para producción.
4. Habilitar la interfaz y `VITE_WORKSPACE_PLANNING_CLOUD_READY` solo después de verificar migraciones, endpoint y `VITE_STUDYHUB_SNAPSHOT_RPC`. Recargar clientes y hacer smoke test con una cuenta de prueba autorizada. Verificar conflicto entre dos pestañas, importación explícita, entrega/descarga privada y persistencia tras recargar. Conservar el artefacto anterior compatible y vigilar conflictos y errores.
5. Para revertir, cerrar escrituras con `disable_planning_writes.sql`, desactivar la bandera de planificación y preservar filas, objetos y colas posteriores. Recuperar lectura con un cliente compatible. Comparar el estado posterior con la copia antes de reconciliar. No restaurar un snapshot antiguo sobre actividad nueva ni reabrir escritura directa. [Procedimiento para la ventana](../StudyHub_2_Procedimiento_Publicacion.md).

## Reproducir

- `npm test` y `npm run build`. La auditoría se ejecutó con `npm audit --json`.
- `node scripts/run-planning-local.mjs --release` con los contenedores desechables documentados. `node scripts/measure-planning-v2.mjs --release` y `node scripts/export-release-scenario.mjs` utilizan datos sintéticos.
- `node scripts/verify-release-browser.mjs` usa Chrome y Playwright locales. Si no están instalados en las rutas predeterminadas, indicar `CHROME_BINARY` y `PLAYWRIGHT_ENTRY`. Crea un perfil temporal y sirve el build en loopback.
- En la referencia permitida y con la barrera CAS ya instalada, usar `node scripts/verify-planning-staging.mjs --enrolled-cloud` con las variables de staging del procedimiento existente. Para el ensayo transaccional, indicar `STUDYHUB_TEST_SUPABASE_CLI` si la CLI autenticada no está en PATH. `node scripts/verify-release-file-picker.mjs` requiere también la clave **publicable de staging** en `STUDYHUB_STAGING_PUBLIC_KEY` y los archivos sintéticos de `.tmp/file-picker-check/`. Las claves administrativas solo se utilizan en el proceso de verificación.
